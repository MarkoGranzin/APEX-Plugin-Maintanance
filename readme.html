Was es tut

APEX-Plugins werden oft „von vielen Händen" gebaut: JS/CSS liegt mal als base64-BLOB im SQL-Export, mal als lose Datei, mal als String mitten im PL/SQL. Es gibt kein package.json, keine einheitliche Konvention. Dieses Werkzeug macht daraus einen wartbaren, automatisch geprüften Bestand:

  • Anbinden & Inventarisieren — mehrere Git-Repos (GitHub/lokal), Plugins und Template-Komponenten erkennen.
  • Normalisieren — jedes Artefakt in ein kanonisches Bündel überführen (die einzige stabile interne API).
  • Testen — Static-First (Lint, retire.js, Golden-Master-Snapshot) plus KI-generierte Verhaltenstests, mit Selbstheilungs-Schleife und Flaky-Quarantäne.
  • Aktualisieren — veraltete Libs per SBOM-Fingerprinting erkennen, updaten, testen, und das Ergebnis über die sourceMap ins Original zurückschreiben (Re-Injektion).
  • Ausliefern & Melden — nur bei grünem Test ein Pull Request (kein Doppel-PR), ein gebündelter E-Mail-Report je Lauf, vollständige History.

Leitprinzipien (die Leitplanken)

🟢 Test-Gate vor Push

Kein Re-Upload ohne grünen Testlauf. Bei Rot: begrenzte Selbstheilung, sonst Rollback + Fehlerbericht — niemals „grün gemogelt".

🔑 Keine Secrets im Klartext

API-Keys/Git-Tokens werden verschlüsselt gespeichert (AES-256-GCM), maskiert angezeigt und nie in Report/Logs geschrieben.

🧩 Normalisierung zuerst

Alles Format-Spezifische passiert vor dem kanonischen Bündel. Danach ist die ganze Pipeline format-blind.

🤖 Deterministik > KI

Übergänge, Extraktion, Re-Injektion sind deterministisch. Die KI sitzt nur an Urteils-Knoten (Testvorschlag, Reparatur, Risiko-Text). Nicht sicher Auflösbares wird markiert, nicht geraten.

Ein Lauf — der Zustandsautomat je Artefakt

ScanRepo fetch + Diff→ Extraktkanon. Bündel→ TestStatic-First + Gate→ UpdateLib-Bump→ Re-InjektionsourceMap→ ReviewSecurity + Code→ PRdedupliziert→ Reportgebündelt

Jedes Artefakt durchläuft diese Zustände einzeln. Eigenschaften des Treibers (src/run/orchestrate.js):

  • Teil-Fehler isoliert — kippt Artefakt A, laufen B/C zu Ende; A landet als failed / zu klären.
  • Resume — nach Crash startet jedes Artefakt am letzten persistierten Zustand, nicht von vorn.
  • Aggregation — genau ein Report und ein History-Eintrag je Lauf, nicht eine Mail pro Artefakt.

Pflege durch Agenten & Review-Gates

Die automatische Pflege läuft wie in einem echten Team — Umsetzung durch einen starken Entwickler, danach zwei unabhängige Reviews. Der Pull Request entsteht erst, wenn Pflege fertig und beide Reviews grün sind.

👩‍💻 Pflege — Web-Entwickler-Agent

Reparatur (Selbstheilung) und Lib-Update kommen von einer Web-Dev-Persona: idiomatisch, schlank, lesbar — nicht nur „Tests grün". Nutzt den AST-Testkontext und vorhandene APIs statt neuer Globals.

Skill-Anker: eigener Umsetzungs-Agent (Persona-Prompt in src/ai/personas.js).

🛡️ Gate 1 — Security-Review (OWASP)

Prüft die Änderung gegen OWASP Top 10 / ASVS & typische APEX-JS-Fallen: XSS (innerHTML, document.write), eval/new Function, hartkodierte Secrets, javascript:-URLs — plus CVE-Libs aus dem SBOM. Findings ab Schwelle blockieren (explizit quittierbar).

Skill: security-review + retire.js/SBOM.

✨ Gate 2 — Code-Review (Qualität)

Ist der Code schön, einfach, lesbar und ohne lose Enden? Erkennt TODO/FIXME, debugger, leere catch-Blöcke, unbenutzte Variablen und übermäßige Komplexität (per AST).

Skills: code-review, simplify.

🚦 Gate-Regel

Sequentiell: Security → Code → PR. Ein Security-Block stoppt schon vor dem Code-Review; jeder Block verhindert den Push und landet als review-blockiert in History/Report. Im Lauf-Automaten ist das der Zustand reviewed.

Die statischen Scans sind die deterministische Untergrenze; die genannten Skills/Agenten werden als injizierbare Reviewer zusätzlich daraufgesetzt (opts.reviewer). Umgesetzt in src/run/review.js.

Das kanonische Bündel

Herzstück der Architektur. JS steckt in APEX an drei Orten — base64-BLOB (create_plugin_file), inline im PL/SQL (add_inline_code/htp.p) und als Referenz (CDN). Der Extraktor führt alles in eine Struktur über; die sourceMap merkt sich die Herkunft, damit ein Fix exakt zurückfindet (Round-Trip byte-identisch).

// src/extract/extract.js — extractArtifact()
{
  artifact: "colorpicker",
  js:            [{ name, code }],   // dekodiert / lose / inline
  css:           [{ name, code }],
  inlineCode:    [{ name, code }],   // aus PL/SQL (T-20)
  referencedUrls:[{ url, version }], // CDN/File-URLs
  sourceMap:     { "widget.js": { type:"plugin_file", sqlFile, fileName } },
  unsafe:        [],                 // nicht auflösbar → markiert, nie geraten
  status:        "ok"
}

Speicherformat (Export/roh/unklar) entscheidet die Extraktion und den groben Test-Pfad; die Laufzeit-Abhängigkeit entscheidet die Testebene: jsdom + apex.*-Shim als günstiger Default, Playwright gegen eine ephemere APEX-Instanz nur dort, wo echtes apex.server.process-Runtime nötig ist.

Einrichtung

Voraussetzung: Node ≥ 20 und git im Pfad.

Am schnellsten: Start.cmd doppelklicken (Windows) bzw. ./start.sh ausführen (macOS/Linux). Das Skript installiert fehlende Abhängigkeiten automatisch und bietet ein Menü: Web-GUI starten, Repo scannen oder Tests ausführen.
# Manuell: Abhängigkeiten installieren
npm install

# komplette Testsuite (sollte grün sein)
npm test

Optional für die spätere Nutzung von Secrets/Provider-Backend:

# Windows PowerShell
$env:AISPP_MASTER_KEY = "ein-langes-geheimes-passphrase"
# macOS/Linux
export AISPP_MASTER_KEY="ein-langes-geheimes-passphrase"

Programmgesteuert über src/config/settings.js (Repos, E-Mail-Empfänger, Cron-Zeitplan, KI-Backend) und src/config/secrets.js (verschlüsselter Secret-Speicher). Repos referenzieren ein Secret nur über eine secretRef — der Key selbst liegt verschlüsselt.

Bewusst offen (Adapter / Folgearbeit)

Die gesamte Logik ist deterministisch gekapselt und über opts injizierbar (git/ai/http/runner/transport) — damit sie ohne Netz/DB/APEX-Instanz testbar ist. Für den Produktivbetrieb sind diese Adapter anzuschließen:

  • Echtes Provider-HTTP & SMTP-Transport, lokale KI-CLI.
  • Ephemere APEX-Instanz (23ai-Container) + Playwright/utPLSQL für Verhaltenstests kritischer Plugins.
  • HTML-Frontend für Dashboard/Triage (die View-Modelle liefern bereits die Daten).
  • Externe Risiko-Signale (GitHub archived, OSV, deps.dev, OpenSSF) für den Score in risk.js.
